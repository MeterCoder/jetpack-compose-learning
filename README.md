# Jetpack Compose Learning

A modern Android application showcasing Jetpack Compose UI, Navigation, and Clean Architecture modular design principles.

---

## 📱 Features

- **Modules Dashboard**: A responsive 2-column grid created with `LazyVerticalGrid` showcasing available learning modules.
- **Hello Module**: A dedicated screen module displaying a custom greeting interface with back navigation.
- **Hello World Module**: A dedicated screen module showcasing an interactive Hello World UI with back navigation.
- **Modular Navigation**: Built using Jetpack Navigation Compose with type-safe route management.

---

## 🏗️ Architecture & Project Structure

The project follows a clean, feature-based package hierarchy for scalability and code segregation:

```
com.example.jetpackcomposelearning
├── MainActivity.kt                       # App entry point displaying GridViewScreen
├── model
│   └── ModuleItem.kt                     # Data model for module grid cards
├── navigation
│   └── NavRoutes.kt                      # Centralized navigation route definitions
├── modules                               # Feature modules
│   ├── hello
│   │   └── HelloScreen.kt                # Hello Screen UI module
│   └── helloworld
│       └── HelloWorldScreen.kt           # Hello World UI module
└── ui
    └── grid
        ├── GridViewScreen.kt             # Main Grid Dashboard & NavHost container
        └── components
            └── GridModuleCard.kt         # Reusable card UI component for grid items
```

## 🛠️ Tech Stack & Dependencies

- **Language**: Kotlin
- **UI Framework**: Jetpack Compose (Material 3)
- **Navigation**: Navigation Compose
- **Build System**: Gradle with Version Catalogs (`libs.versions.toml`)
- **Compatibility**: Android SDK 24 (Min) to SDK 35+ (Target)

## 🚀 Getting Started

1. Clone the repository:
   ```bash
   git clone <repository-url>
   ```
2. Open the project in **Android Studio** (Ladybug / Jellyfish or newer).
3. Let Gradle sync automatically.
4. Run the app on an Android Emulator or connected device (`Run > Run 'app'`).


====================================================================================================
Few Learning Points
====================================================================================================
1. What changes happened in gradle.xml and are they autogenerated or supposed to be pushed?
   • What changed: .idea/gradle.xml contains local IDE project configuration settings generated by
                    Android Studio / IntelliJ (such as local project paths and Gradle test runners).
   • Autogenerated or push?: It is autogenerated by Android Studio.
   • Should it be pushed?: No. It contains machine-specific IDE settings. In standard Android
                     development, .idea/ files are generally kept out of Git or added to .gitignore.

2. What changes happened in libs.versions.toml and are they autogenerated or supposed to be pushed?
   • What changed: We added version references and library dependencies for:
   ◦ navigation-compose (for screen navigation)
   ◦ material-icons-core and material-icons-extended (for icons like Face, Star, ArrowBack)
   • Autogenerated or push?: It is NOT autogenerated. It is Gradle's Version Catalog file
                             (gradle/libs.versions.toml).
   • Should it be pushed?: YES, MUST BE PUSHED. This file defines all the libraries and dependencies
                           needed to build the project. Anyone cloning the repository needs this 
                           file to compile the project successfully.

3. What changes happened in misc.xml and are they autogenerated or supposed to be pushed?
   • What changed: .idea/misc.xml stores project-level IDE configuration like the local JDK version 
                    (e.g., JDK 21), language level, and build output paths.
   • Autogenerated or push?: It is autogenerated by Android Studio based on your local JDK 
                             installation.
   • Should it be pushed?: No (optional). Because developers on different machines might use
                           different JDK paths or versions, pushing this file often causes
                           unnecessary merge conflicts.

4. What is the need for syncing Gradle again and again?
   Gradle Sync is required whenever dependencies or build settings change because:
   1.Downloading Dependencies: Gradle fetches missing library packages (.aar/.jar files) from remote
     repositories (Google Maven, MavenCentral).
   2.IDE Indexing & Code Completion: Syncing updates the IDE's classpath so that imports
      (like androidx.navigation.compose.*) are recognized by the code editor and auto-complete works.
   3.Generated Type-Safe Accessors: In Kotlin Gradle (.kts) with version catalogs, 
     Gradle generates code accessors like libs.androidx.navigation.compose.
     Syncing regenerates these references.
